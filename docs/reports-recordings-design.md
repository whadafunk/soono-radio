# Reports — Recordings (design)

**Status: design approved 2026-11-25; built per `plans/04-recordings.md` (Recordings tab, mix-engine recording, retention sweep, holds). Broadcast Log and Campaigns tabs are placeholders.**
**Depends on the station timezone setting (`station-timezone-design.md`), built first.**

## Intent

The station needs to be able to prove what it broadcast. The Romanian audiovisual
authority (CNA) can ask for the recording of a given period, and the operator
also wants to listen back to the output to monitor it. Today nothing is recorded:
the mix engine sends its output to Icecast and nowhere else.

This is the first part of a new **Reports** section. Recordings go first because
they were asked for specifically. The other two tabs (Broadcast Log, Campaigns)
are a later design — the CNA's requirements for a broadcast journal are not known
yet.

## Goals

- A new sidebar entry **Reports**, directly under **Logs**, opening a page with
  three tabs: **Broadcast Log**, **Campaigns**, **Recordings**.
- The station's final output is recorded continuously to MP3 files whenever the
  station is on air, live shows included.
- The operator can find a recording by date and time, listen to it in the page,
  and download it — one file, or a time range as a single file.
- The operator can configure recording quality, file length, and how long
  recordings are kept; can delete recordings by hand; and can protect a period
  from deletion.
- If recording is supposed to be happening and is not, the operator is told.

## Non-goals

- The Broadcast Log and Campaigns tabs. They exist as tabs with a "coming soon"
  placeholder (the app already has a `ComingSoon` page component).
- PDF export.
- Size-based file rotation. Files are cut by time only (see Decisions).
- Formats other than MP3.
- Recording while the station is Off Air. The mix engine is stopped then; there
  is nothing to record.
- Silence detection, loudness analysis, or any analysis of the recorded audio.
- Copying recordings off the server (NAS, cloud). They live on the server's disk.
- Per-user access rules. The page is as open as the rest of the app is today.

## Anti-goals

- **Recording must never fail silently.** A station that believes it has 60 days
  of proof and has none is worse off than one that knows it has none.
- **Recording must never take the stream down.** A full disk, an unwritable
  folder or a bad setting may stop the recording; the Icecast output must keep
  running.
- **Automatic deletion must never remove a protected recording.**
- No browser pop-ups for confirmations (operator's stated preference,
  2026-11-11): confirm inline, in the page.

## Constraints

- Server disk: 197 GB, 152 GB free after the 2026-11-24 resize. It is shared
  with every other stack on the host.
- The mix engine is LiquidSoap 2.2.5 (`savonet/liquidsoap:v2.2.5`), its script
  generated by the API from `liquidsoap/mix-engine.liq.hbs` on every API start
  and on every settings save (`apps/api/src/services/liquidsoapConfig.ts`).
- Changing anything in that script takes effect only when the mix engine
  restarts — a few seconds of interruption on air.
- The Off Air switch stops the mix engine container
  (`apps/api/src/routes/station.ts`). Off-air periods are not recorded anywhere
  as history today — only a current flag (`supervisor_state.paused`).
- Database changes go through `drizzle-kit generate` (see `CLAUDE.md`).
- A change to the LiquidSoap script or to `docker-compose.yml` must be built
  and smoke-tested before it reaches the live containers (see `CLAUDE.md` and
  the 2026-07-22 outage).

## Approaches considered

1. **The mix engine writes the files itself — chosen.** A second output next to
   the Icecast one. Records exactly what is sent out, with quality settings
   that are separate from the stream's, and keeps recording if Icecast is down.
   Nothing new to run. Costs: changing a recording setting restarts the mix
   engine, and any mix-engine restart starts a new file.
2. **A separate recorder container listening to the Icecast stream.** Captures
   what listeners actually receive and survives mix-engine restarts, but is one
   more container to maintain, records nothing while Icecast is down, and its
   quality is tied to the stream's.
3. **The API records the stream.** Every deploy or API restart would cut a hole
   in the recording. Ruled out.

The operator picked 1: fewest moving parts, and the proof does not depend on
Icecast.

## Decisions made with the operator

- **Files are cut by the clock.** Default one file per hour. A request arrives
  as "3 November, 14:00–16:00"; files that start on the hour map to that
  directly, size-based files do not.
- **Recording quality is its own setting**, independent of the stream's:
  bitrate, sample rate, mono or stereo. Format is always MP3.
  **Defaults: 64 kbps, 22.05 kHz, mono** — about 29 MB an hour, 0.7 GB a day.
- **Retention default: 60 days** (about 42 GB at the default quality). Older
  recordings are deleted automatically.
- **Disk floor, with a protected minimum age.** If free disk falls below a
  floor, the oldest recordings are deleted first, even if younger than the
  retention — but never anything younger than a minimum age, **default 30
  days**. When the floor cannot be met without crossing that age, nothing more
  is deleted and the page warns instead. Accepted risk: the disk can then
  really fill.
- **Hold.** The operator can mark a time range as "keep" with a note (for
  example a complaint under review). Any file overlapping a held range is
  exempt from every automatic deletion and from manual purge until the hold is
  removed.
- **Health warning.** Recording enabled, station on air, and no file being
  written → a visible warning on the Dashboard and on the Recordings tab.
- **Off Air shows as a labelled gap**, not as a missing file.

## Design

### Recording (mix engine)

A second output in `mix-engine.liq.hbs`, fed by the same final `radio` source
that goes to Icecast, rendered only when recording is enabled:

```
output.file(%mp3(bitrate=64, samplerate=22050, stereo=false),
            "/recordings/%Y-%m-%d/%Y-%m-%dT%H-%M-%SZ.mp3",
            reopen_when={0m0s}, fallible=true, <radio, converted to mono>)
```

- One folder per day; the file name is the moment the file was opened, in UTC.
  The mix engine container gets `TZ=UTC` so this does not depend on host
  settings. The page lists, groups by day and names downloads in **station
  time** — the station timezone setting, not the browser's and not the
  container's. Day listing (`?date=`), hold ranges and "older than a date" all
  mean station-local dates.
  *(My call: UTC names are unambiguous across daylight-saving changes.)*
- File length options: **15, 30 or 60 minutes** — values that divide an hour,
  so files always start on a clock boundary. *(My call.)*
- The output must not be able to stop the stream. **This is a gate, not an
  assumption:** `fallible=true` covers only the source failing, and both
  outputs share one clock, so a full disk, a stalled write or an unwritable
  folder could stall the Icecast output too. Before anything else is built,
  the builder proves in a throwaway LiquidSoap 2.2.5 container that the
  stream keeps running through each of those three failures — if needed by
  putting the file output behind a buffer on its own clock. If it cannot be
  isolated inside the script, stop and go back to the operator: that reopens
  the choice of approach (the separate recorder, approach 2).
- New volume `./recordings:/recordings`, writable in the mix engine container,
  writable in the API container (it deletes files). `recordings/` is added to
  `.gitignore`.

### Settings

Two groups, because they take effect differently:

- **Quality and file length** live in the mix engine's own config
  (`liquidsoap/supervisor.json`, schema in `apps/shared`), in a new
  `recording` block: `enabled`, `bitrate_kbps`, `samplerate_hz`, `channels`
  (`mono` | `stereo`), `segment_minutes`. Saving them follows the existing
  mix-engine settings flow, and the form says plainly that applying them
  restarts the mix engine.
  Offered values *(my call)*: bitrate 32 / 48 / 64 / 96 / 128 / 192;
  sample rate 22.05 / 32 / 44.1 kHz. Combinations MP3 cannot encode are not
  offered.
- **Retention and disk floor** live in `data/recordings-config.json` (same
  pattern as `data/logs-config.json`): `retention_days` (default 60),
  `min_free_gb` (default 10), `protected_days` (default 30, never above
  `retention_days`). They take effect immediately, no restart.

Recording is **on by default** once this ships. *(My call — it exists to be
proof; an opt-in that nobody remembers to turn on defeats it.)*

### Finding, playing and downloading (API + page)

The files on disk are the source of truth; there is no database table of
recordings. The API lists a day's files with start time, size and length. A
file's length comes from its size and bitrate, or from the next file's start;
the newest file is marked "recording now".

- `GET /recordings?date=` — the day's files, gaps and holds.
- `GET /recordings/file/...` — one file, with byte-range support so the
  in-page player can seek.
- `GET /recordings/range?from=&to=` — the files covering that period joined
  and trimmed into one MP3, without re-encoding (ffmpeg is already in the API
  image). A range may include the file being written (up to what is on disk).
  If the range contains gaps, the download still works, but the page lists
  every gap in the range before the operator downloads, and the API response
  reports them — a file handed to the CNA must never hide missing minutes.
  *(My call.)*
- `DELETE` for one file, for a whole day, and "everything older than a date".
  Held recordings are skipped and the response says how many were.
- `GET /recordings/status` — recording healthy or not, disk used by
  recordings, free disk, oldest recording kept.
- Hold create / list / remove.

Page sketch (Reports → Recordings):

```
Recordings                                            [ Settings ]
● Recording   ·   41.2 GB used   ·   58 days kept   ·   152 GB free

Date [ 2026-11-24 ▾ ]        Download range [ 14:00 ] – [ 16:00 ] [ ⬇ ]

 13:00–14:00    29 MB    ▶ play    ⬇    🗑
 14:00–15:00    29 MB    ▶ play    ⬇    🔒 held · "CNA request 1182"
 15:00–15:20    10 MB    ▶ play    ⬇    🗑
 15:20–16:05    — Off air —
 16:05–17:00    26 MB    ▶ play    ⬇    🗑
 17:00–         recording now…
```

### Knowing when the station was off air

To label a gap "Off air" rather than "missing", the times of the Off Air /
On Air switch must be kept. A small new table records each switch (time and
direction), written by the two routes in `station.ts`. This table will also
serve the Broadcast Log later. Gaps are labelled in three ways *(the last two
are my call)*:

- overlaps an off-air period → **"Off air"**;
- shorter than 2 minutes → **"Interruption (Ns)"**, shown small and not
  alarming — every mix-engine restart (settings save, deploy) leaves one;
- anything else → **"No recording"**, shown as a problem.

### Automatic deletion

A sweep, at API start and every hour (same pattern as the log and database
sweeps):

1. Delete files older than `retention_days`, except held ones.
2. If free disk is still below `min_free_gb`, delete the oldest remaining
   non-held files until it is not — stopping at any file younger than
   `protected_days`.
3. Never touch the file currently being written.
4. Log what was deleted and why. If step 2 ran, or if the floor cannot be
   reached because what remains is held or protected by age, the status says so
   and the page warns.

### Health warning

Recording is considered broken when all of these hold: recording is enabled,
the station is on air, the mix engine is running, and the newest recording
file has not grown for 60 seconds. The Dashboard shows a warning and so does
the Recordings tab. *(Threshold is my call.)*

The warning is on screen only. Nothing is sent (no e-mail, no push): the app
has no outbound notification channel today, and adding one is its own piece
of work. *(My call — raised with the operator as a known limit: a recording
that stops overnight is noticed when someone next opens the app.)*

## Left to the builder

- The exact LiquidSoap expressions for the mono conversion and for the
  15/30-minute reopen predicate, verified against 2.2.5 in a throwaway
  container before anything touches the live script.
- How the range download joins and trims (ffmpeg concat with stream copy is
  the expected route), including a range that spans a settings change.
- Table and column names for holds and for the on/off-air history.
- Page layout details beyond the sketch; follow the Logs page's conventions
  and the contrast rules in `CLAUDE.md`.
- Unit tests for the two pieces of pure decision logic — which files the sweep
  deletes (given files, holds, retention, free disk) and how gaps are labelled
  (given files and off-air periods) — extracted into dependency-free modules
  as `CLAUDE.md` asks.

## Rollout notes

- Adding the volume changes `docker-compose.yml`, so the deploy recreates the
  mix engine and API containers: a short interruption on air.
- First recordings appear only after that deploy; nothing before it can be
  recovered.
